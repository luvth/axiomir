## TL;DR

The working tree is a coherent, well-engineered hardening pass: it adds **cryptographic receipt/evidence authenticity** (HMAC-SHA256 over host-configured `TrustRoot`s) and a **deterministic producer** (`axiom-producer`) that answers "who produces Axiom?". Build is clean, clippy is clean (one trivial unused-import warning), and all tests pass.

The crypto design is sound — keyed HMAC under host-held secrets, constant-time compare, no secrets in the module, wrong-key/forged/empty tags rejected. **One headline gap remains: the textual/parser path never populates `Evidence.provider` or `Evidence.signature`, so the new enforced-evidence-authenticity gate is unreachable from real modules.** It only works for evidence constructed directly via `Module::add_evidence` in unit tests. There are also two smaller correctness issues in the producer's literal rendering.

## What changed (summary)

1. **`axiom-core/src/crypto.rs` (new)** — `TrustRoot`, `sign`, `verify`, `sign_evidence`, `verify_evidence_signature` via `hmac`/`sha2`/`hex`. Constant-time compare via `hmac::Mac::verify_slice`.
2. **Receipt authenticity** — `Receipt.signature` changed from `Option<String>` to `Vec<u8>` (empty ⇒ unsigned ⇒ rejected). `Receipt::verify_integrity` now takes `&[TrustRoot]`, checks tamper-evidence **and** HMAC authenticity. `add_receipt` signs under a `TrustRoot`. `Module::derive` binds the receipt to the derivation's *actual* input hash (`ReceiptInputMismatch`) and requires a trust root for live tool calls.
3. **Evidence authenticity** — `Evidence` gained `provider`. `Module::verify_evidence_authenticity` + runtime `EvidenceForgery` error enforce that `trust=trusted` evidence carries a verifiable signature when trust roots are configured.
4. **Verification gate hardened** — untrusted evidence auto-attaches a mandatory `SourceSupport` obligation; `discharge` now rejects claim-ids as discharging authority (`discharged_by ∈ E ∪ R`).
5. **Producer** — new `axiom-producer` crate: `ReasoningPlan` → deterministic Axiom text (with `produce_from_json`). Wired into the CLI demo 8.
6. **Semantics fixes** — transitive context inheritance, full-claim-set contradiction/merge scanning, assumption-retraction on invalidation, parser `unreachable!()` → proper diagnostics, spec/threat-model updates.

## Strengths

- **Correct threat model.** Uniform `trust = trusted` ⇒ signature required; `unverified`/`untrusted` ⇒ admitted. No silent acceptance of forged trust.
- **Receipt binding is real.** `inputs_hash` is recomputed from the derivation's actual input values and compared, so a self-consistent receipt built for different inputs cannot attach. Verified consistent at live-exec (`runtime.rs:664`) and replay (`runtime.rs:674-677`).
- **Fail-closed live execution.** Live `ToolCalculator` receipt requires a matching configured `TrustRoot`; unknown provider ⇒ `UnknownTrustRoot`. Good.
- **Demo secret is clearly marked** "do-not-use-in-production" and the host is the only one who supplies trust roots.
- **Tests lock behavior:** `receipt_tampering_detected`, evidence forgery, six automatic contradiction kinds, incremental invalidation frontier.

## Findings

### F1 — Evidence authenticity gate is unreachable from real modules  (HIGH)
`Runtime::exec_evidence` calls `self.module.add_evidence(label, media, v, trust_class, media, media)` — the **provider argument is `media` (the media-type string), not a real provider identity** (`runtime.rs:345-352`). It is never set from the textual `evidence` statement (the parser has no `provider` clause). Consequently `ev.provider` is always the media type (e.g. `"text/plain"`), which never matches a configured `TrustRoot.provider`.

Compounding this, **no code path ever sets `Evidence.signature`** for text/producer evidence (it stays `None`). So the enforced path at `runtime.rs:359` (`EvidenceForgery`) can only fire if a module author hand-writes `trust=trusted` *and* somehow supplies a matching provider+signature — impossible through the language today.

Net effect: the threat-model's "Evidence authenticity is enforced" claim is **only true for the `Module::add_evidence` unit-test path**, not for anything a parser/producer emits. Either:
- (a) add a `provider = <ident>` clause to the `evidence` grammar, thread it through `exec_evidence`, and have the host (or a producer) populate `signature` via `crypto::sign_evidence` before execution; or
- (b) downgrade the threat-model residual-risk note to state authenticity is *only* enforced for programmatically-constructed evidence, not textual modules.

The unused `verify_evidence_authenticity`/`sign_evidence`/`Module::add_obligation`(evidence path) surface suggests this wiring was intended but not finished.

### F2 — `Literal::Rational` in the producer is a no-op / latent mismatch  (MEDIUM)
`crates/axiom-producer/src/lib.rs:33` renders `Literal::Rational(n)` as a bare integer (`n.to_string()`) while typing it `: rational` (line 41). The textual Axiom language has **no `Rational` literal syntax** — `5` lexes to `Expr::Num` → `Value::Num(Num::Int(...))`. The `Rational`/`Int` distinction in the producer therefore collapses to the same token and the declared `rational` type is only loosely checked. It is not exercised by any test (all JSON fixtures use `Int`). Recommend: drop the `Rational` variant or render it explicitly if the language gains rational syntax; document that integer literals become `Int`.

### F3 — Producer step output-type inference is heuristic and wrong for `core.*` on quantities  (LOW)
`crates/axiom-producer/src/lib.rs:157`: `let ty = if s.op.starts_with('q') { "quantity" } else { "rational" };`. `core.add`/`core.div` on quantity inputs would be emitted `: rational`, mismatching the actual quantity result type. The sample plan uses only `qmul`, so tests pass, but a JSON plan with a `core.*` step over quantities would emit a type-mismatched claim. Use the op registry or an explicit per-step type to render the output type.

### F4 — `verify_evidence_authenticity` is dead on the replay path  (LOW)
`Module::verify_evidence_authenticity` (`lib.rs:1501`) is only referenced by tests; the runtime never calls it during replay. `exec_evidence` does an inline check instead. Either call `verify_evidence_authenticity` in the replay/load path (so a forged module is rejected before any execution) or remove it to avoid a misleading "enforced on replay" implication in the threat model.

### F5 — Trivial: unused import  (INFO)
`crates/axiom-producer/src/lib.rs:17` `use axiom_types::num::Num;` is unused (clippy-confirmed). Remove it.

## Recommendations (priority order)

1. **Fix F1** — wire `provider` + `signature` into the textual `evidence` statement (and producer), or correct the threat-model to scope the enforcement to programmatic evidence only. This is the only finding that affects the stated security guarantees.
2. **Fix F2/F3** — make producer literal/type rendering exact; add a unit test that round-trips a `Rational` and a `core.add`-over-quantities plan.
3. **Resolve F4** — invoke `verify_evidence_authenticity` on the replay/load path or remove it.
4. **Cleanup F5** — drop the unused import.

---

## Bottom line

The diff is high quality and the verification gate *design* is correct and well-tested at the unit level. Ship-ready **except** for F1: the evidence-authenticity enforcement is currently unreachable through the actual language surface, so the threat-model's strongest new claim ("forged high-trust evidence is rejected") holds only for directly-constructed evidence, not for parsed/produced modules. Address F1 before relying on evidence authenticity in production.
